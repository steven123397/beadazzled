# List 滚动帧率（2026-11-02）

状态：验收记录，回答 Checkpoint 4 的「1000 条滚动 60fps」。不改预算阈值。

关联：`bza-jdx`（Checkpoint 4）、[SPEC-list](../spec/SPEC-list.md) 验收标准 1、
`bza-bee`（测量脚本与 CI 接线）、`CONSTRAINTS.md` 的「列表滚动」。

## 问题

Checkpoint 4 需要 1000 条票据下滚动稳定 60fps。仓库里原有的 E2E 断言直接对
Vite dev server 计时，在这台机器上出现两种结果：p50 稳定在 16.6–16.9ms，但
p95 在 18–40ms 之间波动，单次最长帧到 79ms，同一份代码有时通过、有时失败。

需要分清：是产品本身掉帧，还是 dev 构建与测量环境的问题；以及一个速度、
一种分组是否足以支撑「60fps」这个结论。

## 方法

1. 用 `VITE_E2E=1 npm run build` 生成**生产构建**，把 Playwright 的数据 seam
   编进去；默认 `npm run build` 仍然会 tree-shake 掉它（`check:bundle-seam`
   会验证这一点）。
2. `vite preview` 提供静态产物，Chromium 打开 `#/w/p1/list`，注入 1000 条固定
   票据。
3. 三个场景，各跑 5 轮：
   - `steady`：从顶部开始，每帧 48px（约 1.3 行/帧），120 帧；
   - `fling`：从顶部开始，每帧 240px（约 6.7 行/帧，接近真实滚轮 fling 的低端），
     150 帧，覆盖整份列表直到尾部；
   - `grouped`：从 20,000px（越过 open 分组）开始，每帧 48px，150 帧，
     `group=status`，跨越状态分组头并走到列表后段。
4. 每个场景先把滚动位置跳到起点、等两帧再开始采样；记录 `requestAnimationFrame`
   的时间差、起始/结束 `scrollTop` 与移动距离。p50/p95 取 5 轮中位数，`max`
   取所有轮次里**实际出现过的最长帧**（不能用中位数，否则一次 GC 停顿会被
   藏起来）。移动距离低于场景下限即判失败，避免因触底钳制而「只测了开头」。
5. 预算沿用原 E2E 断言的数值：p50 < 20ms、p95 < 24ms、max < 50ms。

命令：`npm run measure:scroll`（`scripts/measure-scroll.mjs`）。

环境：Windows 11、i5-13500H、平衡电源计划；测量时浏览器与其他应用同时运行。

## 结果

生产构建，三个场景各 5 轮：

| 场景 | p50（中位） | p95（中位） | 最坏帧 | 移动距离 |
|---|---:|---:|---:|---:|
| steady 48px/frame，从 0 | 16.7ms | 18.4ms | 23.6ms | 5,760px |
| fling 240px/frame，从 0 | 16.7ms | 18.7ms | 29.0ms | 35,432px（到尾部） |
| grouped 48px/frame，从 20,000 | 16.7ms | 17.9ms | 25.5ms | 7,200px |

单轮明细：

| run | steady p50/p95/max | fling p50/p95/max | grouped p50/p95/max |
|---:|---|---|---|
| 1 | 16.8 / 18.4 / 22.4 | 16.7 / 18.7 / 23.3 | 16.7 / 17.9 / 24.5 |
| 2 | 16.8 / 18.3 / 20.6 | 16.6 / 19.0 / 22.5 | 16.6 / 17.8 / 21.9 |
| 3 | 16.7 / 18.4 / 23.6 | 16.6 / 18.5 / 29.0 | 16.6 / 17.9 / 19.5 |
| 4 | 16.7 / 19.1 / 22.6 | 16.7 / 18.4 / 22.3 | 16.7 / 18.0 / 18.5 |
| 5 | 16.7 / 18.7 / 22.6 | 16.7 / 18.7 / 23.5 | 16.7 / 18.7 / 25.5 |

对照：同一测量跑在 dev server（React development build）上时，p50 仍是
16.6–16.9ms，但 p95 为 22–40ms、max 到 79ms，且随宿主负载明显漂移。

## 结论

1. **生产构建达标，且不只在慢速滚动下成立**：三个场景的中位帧都是 16.7ms
   （满帧 60Hz），p95 17.9–18.7ms，最坏帧 23.6–29.0ms。fling 场景实际移动了
   35,432px（从顶部直到列表尾部），grouped 场景从 20,000px 起跨越了状态分组头；
   快速滚动、分组渲染和列表后段都没有持续掉帧。
2. **dev server 不能作为 60fps 证据**：同一份代码在 React development build
   下挂载行的成本接近翻倍，p95 会被推到预算边缘。原 E2E 断言因此从
   `tests/e2e/list.spec.ts` 移到 `npm run measure:scroll`，阈值不变，测量对象
   改为真正发布的产物。
3. **CI 接线仍归 `bza-bee`**：本脚本目前只本地运行；`CONSTRAINTS.md` 中该项目
   的「待接线」状态不变。
4. 环境噪声仍在：测量机上同时运行浏览器与其他应用。三个场景 × 5 轮的 p50/p95
   和最坏帧都远离预算，结论不依赖某一轮的偶然值。后续如果增加更快的 fling
   （>400px/frame）或更长采样，可在同一脚本里追加场景，不必改门槛。
