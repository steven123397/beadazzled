# 内存测量（2026-11-04）

状态：`bza-bee` 记录，ADR-0011 的测量依据。不改变产品行为。

## 环境

| 项 | 值 |
|---|---|
| 系统 | Windows 11 Home China 10.0.26300 |
| WebView2 Runtime | 156.0.4314.58（Edg/156.0.4314.58） |
| 构建 | release 0.1.0，`src-tauri/target/release/beadazzled.exe` |
| 工作区 | 临时 bd 数据库，由 `bd import` 导入 1 / 1000 条 fixture |
| 工具 | `npm run measure:memory`（Playwright 通过 DevTools 连接到 WebView2） |

## 方法

1. 用 `BEADAZZLED_CONFIG_DIR` 指向隔离的临时配置，`WEBVIEW2_USER_DATA_FOLDER`
   指向隔离 profile，启动 release 二进制。
2. 通过 `--remote-debugging-port` 连接 WebView2，等列表进入
   `data-state="ready"` 后开始采样。
3. 每次采样对 host 进程与该 profile 下的全部 `msedgewebview2.exe` 求
   `WorkingSet64` 之和；先做一次 GC，再读取 JS heap 与 DOM 节点数。
4. 先测 1 条票的基线（2 次采样取中位），再测目标规模（默认 5 次取中位）。

## 结果

### 总工作集

| 条数 | 样本 | 中位 | 说明 |
|---:|---|---:|---|
| 1 | 437 / 449 MB | 449 MB | 固定开销（第一轮） |
| 1 | 452 MB | 452 MB | 最终构建基线（9 次采样） |
| 20 | 438 MB | 438 MB | 与基线同量级 |
| 1000 | 457 / 457 / 457 MB | 457 MB | 最终构建前，DevTools 连接 |
| 1000 | 467 MB | 467 MB | 最终构建（5 次采样） |

同一构建、不连接 DevTools、启动后静置 12s 的对照测量：

| 条数 | 总工作集 |
|---:|---:|
| 1 | 436.2 MB |
| 1000 | 445.5 MB |

即 1000 条票相对 1 条票的数据增量约 **+9 至 +15 MB**；DevTools 连接本身约增加
10–20 MB。

### 进程构成（1000 条，DevTools 连接）

| 进程 | 工作集 |
|---|---:|
| `msedgewebview2`（browser） | 142 MB |
| `msedgewebview2`（GPU） | 110–129 MB |
| `msedgewebview2`（renderer） | 95–99 MB |
| `msedgewebview2`（utility ×2） | 约 67 MB |
| `beadazzled.exe`（host） | 38 MB |
| crashpad handler | 16 MB |

前端本身：JS heap 5.5 MB，DOM 约 1,047 个节点（列表虚拟化生效）。

## 结论

- 150 MB 的原预算在任何 WebView2 构建上都不可达；固定多进程开销约 430 MB。
- 应用侧的数据成本很小且可测：1000 条票增加约 9 MB。
- 按 ADR-0011，预算改为「总工作集 ≤600 MB 且 ≤1 条基线 +50 MB」，
  `measure:memory` 同时测量两者并报告增量。
- 已知边界：工作集按进程求和，共享 DLL 页会被重复计数；不同 WebView2 /
  Windows / GPU 驱动的绝对值和构成会漂移。增量门槛比总量更能反映应用回退。
