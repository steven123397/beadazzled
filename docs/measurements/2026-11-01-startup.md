## 方法

`npm run measure:startup -- --runs=20 --warm-runs=20`

1. 启动 release 二进制，计时从 Node `spawn()` 开始，包含进程创建、WebView2 初始化与前端加载。
2. 终点使用应用自己写出的原生标记：Rust `on_page_load` 的
   `PageLoadEvent::Finished`（WebView2 `NavigationCompleted`）。脚本通过
   `BEADAZZLED_STARTUP_TRACE` 指向的文件读取时间戳；不启用 DevTools 协议，
   避免给被测启动增加额外开销。
3. **冷启动**：每次用新的 `WEBVIEW2_USER_DATA_FOLDER`（全新 WebView2 profile），
   接近安装后首次启动。
4. **热启动**：先做一次不计数的预热，随后复用同一个 profile 连续启动。
5. 每次测量后结束进程树并清理该 profile 的 WebView2 子进程，避免残留进程
   占用 profile 导致后续样本变慢；样本之间等待约 0.5s。
6. P50/P95 采用 nearest-rank（P95 为升序后第 `ceil(0.95n)` 个样本）。

**标记与“可交互”的偏差**：同一构建上用 CDP 校准三次，页脚（React 首次 commit）
比 `NavigationCompleted` 晚约 59–60ms。因此下表数字是“页面加载完成”时刻，
可交互时刻约再加 60ms；这个偏差不足以改变达标结论。

## 解释与限制

- 冷启动两轮 P95 分别为 947ms、909ms，距离 2.0s 预算有约一倍余量；单轮出现过
  一次 2085ms 的离群值，但 P95 仍达标。
- 热启动两轮 P95 分别为 873ms、990ms，均超 800ms 预算；P50 为 624ms / 681ms，
  在预算内。按 CONSTRAINTS，性能预算当前为 **warn**，本次只记录、不阻断；
  连续三次测量超标时才需要提 issue 或重设预算。加上约 60ms 的 commit 偏差后
  结论不变（仍超）。
- 开发机的 OS 文件缓存通常是热的，真实重启后的首次冷启动可能更慢；本次
  “冷启动”只隔离 WebView2 profile，不等同于清空系统文件缓存。
- 测量期间未禁用 Defender 实时扫描，也未固定 CPU 频率；单个样本存在
  ~1.1–2.1s 的离群值，P95 比 P50 更能反映尾部体验。两轮之间相差 ~10–15%，
  说明该机器上的测量噪声不小，后续 ratchet 前应先在 CI 固定环境复测。

## 复现

```bash
npm run measure:startup -- --runs=20 --warm-runs=20
npm run measure:startup -- --runs=0 --warm-runs=10   # 只测热启动
npm run measure:startup -- --json                     # 机器可读
```

脚本在 release 二进制缺失时会自动执行 `tauri build --no-bundle`（`--no-build`
可禁用）。`BEADAZZLED_STARTUP_TRACE` 只在被显式设置时写文件，正常启动不产生
任何文件。
